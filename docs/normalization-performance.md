# 正規化検索の内訳と局所改善

## 対象と条件

正規化検索の段階1として、候補抽出後の本文処理と索引復元の時間を分離した。固定seedの合成1,000文書、本文合計1,108,414バイトを使い、希少語、多数候補・多数一致、多数候補・一致なし、1コードポイントの多数一致・少数一致、該当なしを分けた。実ノートや検索履歴は使っていない。

`normalized-compare-01` はZig 0.17.1 / ReleaseFast、構築3回、予熱2回、各検索10回。基準と改善候補は同じコーパスを参照し、検索語順・variant順を固定seedで入れ替え、search/scanと計測有無の先後を交互にした。ファイルキャッシュは破棄していない。

チーム内のビルド・テスト・別測定は停止したが、ホスト全体の負荷は統制していない。この結果は単一環境の合成スモーク確認であり、性能保証、実KBでの品質・速度、別環境への一般化には使わない。構築はvariant順が固定で各3回のみなので、構築時間の差の因果は判断しない。p95はnearest-rankで、少数反復では最大値に近い。

## 計測した範囲

`-Dprofile=true` の専用ビルドは、標準エラーへ内容・パス・検索語を含まないJSONを1行出す。通常ビルドは計測状態と時計を使わない。CLI全体の時間・peak RSSは、無計測版を新規プロセスで起動して取得した。

| 区間 | 含める処理 |
| --- | --- |
| read | 索引ファイルの読み込み、または文書の走査・読み込み |
| checksum / decode | チェックサム検査 / 保存形式の検査と復元 |
| query_prepare | 検索語の検証と正規化 |
| candidates | gram選択、posting照合、候補処理のうち別区間以外 |
| span_transform | 原文の由来対応表を含む本文の正規化 |
| index_of | 検索表現での連続一致 |
| original_span | 一致した区間の原文バイト区間の照会 |
| output / cleanup / other | 行・抜粋・出力 / 明示解放 / 残りの処理 |

区間は重複しない。`total_ns` は別枠の総時間で、内訳と加算しない。最短posting件数、全gram通過後の候補件数、本文検証数、一致数、本文変換数・入力バイト数、位置照会で訪れた要素数も記録した。scanや正規化後1コードポイントの検索ではposting候補は0で、本文検証数が全走査数になる。

今回、計測版/無計測版のCLI中央値比は基準で0.948〜1.026、候補で0.946〜1.018だった。計測版が速く見える条件もあり、時計のオーバーヘッドと実行環境の揺れを分離できない。内訳の割合をCLI時間から差し引いたり、専用ビルドの時間だけで速度を判断したりしない。

## 観測と変更

最初の探索では、多数候補・1コードポイント走査のspan付き本文正規化が約40〜42ms、原文区間の照会は多数一致でも約0.84msだった。希少語・該当なしではチェックサムが約2.7msを占めた。すべてを位置照会だけの問題とは扱わない。

コード上では各中間コードポイントについて、必要数を得る呼び出しと出力を得る呼び出しで分解を2回実行していた。変更後は8要素のスタック領域へまず出力し、収まる場合は1回で使う。収まらない場合だけ必要数を確保して全量を再試行する。分解規則、上限判定、合成制御、原文の由来追跡、保存形式は変えない。この通常経路の呼び出し削減はソースから確認できる事実であり、以下の時間差とは区別する。

| normalized search条件 | 本文検証 / 一致 | CLI中央値 ms 基準 → 候補 | p95 ms 基準 → 候補 |
| --- | ---: | ---: | ---: |
| 希少語 | 1 / 1 | 6.28 → 6.34 | 6.80 → 7.10 |
| 多数候補・多数一致 | 1,000 / 1,000 | 51.07 → 41.23 | 53.60 → 42.79 |
| 多数候補・一致なし | 1,000 / 0 | 47.98 → 39.39 | 51.22 → 40.48 |
| 1コードポイント・多数一致 | 1,000 / 1,000 | 51.45 → 42.70 | 53.09 → 43.71 |
| 1コードポイント・少数一致 | 1,000 / 1 | 50.08 → 40.68 | 52.65 → 41.44 |
| 該当なし | 0 / 0 | 6.30 → 6.32 | 6.80 → 6.71 |

広い4条件のCLI中央値は約17〜19%短かった。計測版の同条件のspan付き正規化は約41〜42msから約32.5〜32.9msへ変化した。normalized scanのCLI中央値は6条件で約13.8〜16.7%短い観測だった。いずれもこの合成スモークの結果であり、一般的な高速化率としては扱わない。literal検索と、normalized索引上のliteral走査を別条件で測り、小さい時間差は正負に混在した。

## 容量・RSS・構築・互換性

| 項目 | 基準 | 候補 |
| --- | ---: | ---: |
| literal索引 bytes | 3,046,513 | 3,046,513 |
| normalized索引 bytes | 3,007,125 | 3,007,125 |
| literal構築中央値 ms | 26.10 | 29.32 |
| normalized構築中央値 ms | 67.20 | 64.77 |
| normalized構築peak RSS中央値 MiB | 13.03 | 13.08 |
| normalized search多数一致peak RSS中央値 MiB | 7.84 | 7.77 |

MiBは1,048,576バイト。RSSは子プロセスの生存期間のhigh-water markであり、正規化の確保量そのものではない。小さいRSS差や構築3回の時間差は改善の根拠にしない。全条件のRSS・p95は[匿名要約JSON](benchmark-results/normalized-compare-01.json)に保存した。

保存形式はv2のまま。同じmodeの基準・候補・計測有無の索引は、容量とSHA-256がすべて一致した。基準が作った索引を候補で読み、その逆も読む36条件で、独立期待結果と自身の索引を読む場合の全CLI出力が一致した。索引には文書パスが含まれるため、別runの索引サイズとは直接比較しない。

## 正しさの確認

- 既存14語と追加8語を、literal索引/literal検索、normalized索引/normalized検索、normalized索引/literal走査の計66条件で検証した。
- PythonのNFKC→casefold→NFKCと原文各行の照合で期待集合・原文行番号を求め、search/scan、基準/候補、計測有無の全出力を比較した。正規化後のバイト位置を原文へ転用していない。
- gram集合から独立に求めた最短posting数・候補数・検証数・一致数が計測値と一致した。
- 展開、半角濁点、結合文字の並べ替え、複数行の原文抜粋を手書きの4ケースで確認した。CLIにはoffset/endが出ないため、バイト区間そのものは既存Zig単体テストの担当範囲とする。
- 実装担当が公式Unicode適合、原文span、上限境界、確保失敗を検証し、追加の8要素超過fallbackも確認した。評価runnerの単体テスト7件も成功した。
- 計測前後のバイナリと生成文書のハッシュが一致した。

## 比較候補の扱い

正規化本文の保存、spanなしの本文照合後に一致文書だけをspan付きで再変換する方法は、今回は実装比較していない。実装した局所変更と同じ強さの測定根拠はない。

これらは非一致候補のspan作成を省ける可能性がある一方、多数一致では原文区間復元の再変換が残る。spanなし照合には追加変換、保存案には索引容量・読み込み・形式互換性のコストがある。今回は全候補の本文変換が支配する観測と、分解の重複実行という具体的な箇所を踏まえ、形式を変えない局所変更を先に採用した。保存を不要と結論したわけではなく、必要なら多数一致・少数一致を分けた別実験とする。mmap・常駐化は比較していない。

## 再現方法と記録

同じ計測導入を含む基準・候補のそれぞれで、通常版と`-Dprofile=true`版を事前にビルドする。構築・テストを終え、他の重い処理と時間帯を調整してから実行する。

```sh
python3 -B scripts/test-benchmark-normalized.py
python3 -B scripts/benchmark_normalized.py \
  --run-id normalized-reproduction-01 \
  --variant baseline .local/benchmarks/baseline-plain-v2/bin/zigurui .local/benchmarks/baseline-profile/bin/zigurui \
  --variant candidate .local/benchmarks/candidate-plain/bin/zigurui .local/benchmarks/candidate-profile/bin/zigurui \
  --provenance baseline=.local/benchmarks/baseline-provenance-v2.json \
  --provenance candidate=.local/benchmarks/candidate-provenance.json \
  --size 1000 --index-repeats 3 --warmups 2 --repeats 10 \
  --require-index-identity
```

runnerは新規run-idだけを受け付け、文書・索引・診断を削除しない。新しい索引を生成するので、保存形式の実験時は`--require-index-identity`を外して差を確認できる。ただしこのオプションを外しても異形式の相互読み込みを検証したことにはならない。

raw、ビルドのprovenance、基準のnormalizerへ戻す逆差分とハッシュ検証はローカル記録に保持した。逆差分は作業ツリーへ適用せず、候補文字列へメモリ上で適用して基準のソースハッシュと一致させた。公開要約は固定項目のみを投影し、端末情報、絶対パス、variant自由名を含まない。rawと公開要約の対応ハッシュ、各実行ファイルとrunnerのハッシュも記録した。

基準は未コミットの計測導入状態なので、公開要約のハッシュだけから基準ソース全体を再構成することはできない。再実行には、ローカルで保持した基準バイナリまたは対応する計測導入状態と逆差分が必要。実KB評価、別環境での再実行、負荷を統制した性能比較は未実施である。
