# 索引容量と差分更新の設計案

状態: 統合前のローカル採用候補。v2読取互換・v3新規保存・明示的な差分更新・変更なし早期終了を実装済み。実KBは使用していない。

## 目的と範囲

索引のディスク容量を減らし、文書の追加・変更・削除後に未変更文書のN-gram計算を省く。保存した原文だけで検索できる性質、検索結果・原文位置、失敗時の旧索引保持を維持する。

「差分更新」は索引の更新を指し、`zigurui update`による実行ファイルの更新と区別する。ファイル監視、mtimeだけでの判定、追記ログ、保存原文の削除、圧縮状態のままの検索は今回の対象外。

## 容量の内訳と候補

基準はmain `aa410952`。既存の固定seed合成コーパス生成器を使い、100・1,000文書、literal・normalizedをDebugビルドで索引化した。容量はビルドの最適化モードとは別で、今回の構造では同じ入力なら保存内容が決まる。合成文書の絶対パス長も容量に含まれる。

`scripts/evaluate-index-size.py`はv2索引を読み取り、チェックサム・構造を確認して内訳を集計する。ID以外の部分を変えず、IDを実際に符号化したバイト数から候補の総容量を算出する。新形式の追加ヘッダーや新しいdecoderを含む実装比較ではない。

| 1,000文書 | literal bytes | normalized bytes |
| --- | ---: | ---: |
| 元の本文 | 1,059,386 | 1,059,386 |
| パス | 147,999 | 147,999 |
| 文書ID | 1,605,488 | 1,590,328 |
| ヘッダー・件数・長さ・gram | 27,240 | 27,078 |
| 現行索引の合計 | 2,840,113 | 2,824,791 |
| IDを固定4バイトにした容量モデル | 2,037,369（28.3%減） | 2,029,627（28.1%減） |
| IDを可変長整数にした容量モデル | 1,611,174（43.3%減） | 1,607,464（43.1%減） |
| IDを差分＋可変長整数にした容量モデル | 1,435,311（49.5%減） | 1,433,254（49.3%減） |

100文書では差分と直接の可変長整数は同容量で、両モードとも全体約47.5%減。IDがすべて1バイトで表せる範囲だからであり、大きい集合でも両者が等しいという意味ではない。

本文の定型性やgramの出現頻度に依存する合成データの結果で、実KBの削減率には一般化しない。読み込み後にusize配列へ展開する限り、ID配列のRAMは減らない。この容量内訳の評価自体では時間・RSSを計測していない。後続の合成スモークで時間・ピークRSSを観測したが、背景負荷を統制した精密測定ではなく、一般的な改善率や圧縮後の内部配列RAM減少を示すものではない。

第一候補は差分＋可変長整数。固定4バイトを単純な比較対象とする。本文圧縮、ビットマップ混在、パスやgram辞書の圧縮は、現時点の容量内訳と責任範囲から後順位とする。

## 差分更新の内部契約

`src/incremental.zig`が差分判定とpostingsの再利用を所有する。現在の文書集合と有効な旧Indexを受け取り、変更があれば旧索引と同じmodeの独立した新Indexを返す。文書数・パス・本文・文書順がすべて一致すれば、変更件数とindex=nullを返す（詳細は[変更なし更新](#変更なし差分更新の局所試作)）。

- パス完全一致で識別し、本文のバイト一致で未変更とする。mtimeが同じでも本文が変われば変更とする。全ファイルの走査・読み取りは必要。
- 追加・変更した文書だけ`Index.initMode`でN-gramを生成する。未変更文書のgramと文書の関係は旧postingsから取得する。
- 削除文書の関係は破棄する。移動・改名は削除＋追加として扱う。
- 文書IDは保存世代内の配列添字。新しい文書順に付け直し、未変更IDも写像する。IDの永続的安定性や墓標は導入しない。パス順を呼び出し側で維持すれば全再構築とバイト単位で同一になる。
- gramとpostingsは新Indexが所有し、原文・パスは呼び出し側の現在文書を借用する。旧Indexの解放後も新Indexを使用できる。
- 重複パスを拒否する。メモリ確保失敗でも旧Indexと現在文書を変更しない。

変更がある場合、再利用によって省くのは未変更文書の正規化とN-gram生成であり、ファイル読み取り・postings全走査・新しい一覧の構築・索引全体の再保存は残る。完全一致の早期終了では新しい一覧の構築と再保存を省くが、全ファイル読取と旧索引の完全検証は行う。後続の条件付き合成比較はあるが、一般的な高速化は保証しない。

## 保存形式・CLIの契約

- 新規の通常構築と差分更新はv3を保存し、postingsのIDは先頭の絶対IDと後続差分をcanonicalなbase-128 varintで表す。件数・原文・gramはv2と同じ表現を保つ。
- v3は検索profileの後に長さ付きsource rootを1つ記録する。CLIはrealpathで解決した絶対ディレクトリを必ず保存する。索引には既に文書の絶対パスと原文が含まれており、rootも同じ私的データとして扱う。診断、stdout、profile、公開要約へrootを追加しない。容量評価はrootのバイト数だけを出力し、文字列を出さない。
- v2は検索・schemaで読み込み可能。root情報がないため差分更新は拒否し、通常indexで明示的に再構築してから導入する。自動変換や暗黙の全再構築はしない。
- `index [--mode ...] --incremental <directory> [<index-file>]`だけで差分更新を起動する。通常indexと同じ設定・既定保存先を使う。旧索引の欠落・破損・mode不一致・root情報欠落・canonical root不一致では書き込まず失敗する。
- 検索時にはrootの実在を確認しない。root照合は差分更新だけ。別名のシンボリックリンクで同じcanonical rootを指す場合は同じ集合とする。文書内のsymlink除外は既存のまま。
- IDは世代内の添字へ詰め直す。永続IDや削除墓標を形式に導入しない。更新後のpostingsを全体保存する。
- decoderはID列を確保前に走査して、途中切れ・過長表現・ゼロ差分・整数overflow・範囲外IDを検証する。v3の文書・posting・展開後ID配列の合計に1GiBの上限を設ける。v2読取は2GiBとし、既存の1GiB未満のv2ファイルとの互換性を保つ。圧縮バイト数だけで過大確保を許さない。
- 旧版はv3を読めない。戻す場合は旧版バイナリで原文から別の保存先へ全再構築する。旧索引の保存が必要なら新しい版のindexの実行前に別の保存先を選ぶ。
- 失敗時は従来の原子的保存経路を維持する。今回も実ユーザー索引を変換・変更せず、合成fixtureだけで検証する。

## 他の変更との接続

ランキングは`Index.documents`のpath/textとMatch配列だけを使い、保存形式や永続IDに依存しない。`search.zig`の契約は変更していない。

`main.zig`での変更はincrementalのimport、helpとエラー案内、index分岐、Arguments/parseArgumentsの新フラグ、原子的保存の小さな検証用関数、対応テスト。search/scanのfindMatchesやprintMatchesは変更していない。ランキングとの統合ではhelp・Arguments・parseArgumentsの両方の追加を保持する。

## 検証と記録

基準・合成文書・v2の容量内訳はworktree内`.local/storage-evaluation/`に保持する。v3実ファイルの追加比較と検証結果も同じ場所へ保存し、既存結果を上書きしない。容量の公開用レポートに本文・パス・rootを含めない。hashとバイト数だけを出す。

差分更新の単体テストは、追加・変更・削除、ID順移動、同一内容での再実行、空集合との相互更新、旧索引解放後の利用、重複パス拒否、両modeで全再構築の保存バイトと一致、独立した期待文書とAND検索、全確保失敗経路を対象とする。

CLIの結合テストは、両mode、v2検索互換と差分更新拒否、設定・既定索引、canonical root別名、root/mode不一致・欠落・破損の拒否、元root不在の検索・schema、実際の書込サイズ制限での旧索引保持を確認する。書込・sync・replaceの各段階の注入失敗は同じ保存関数の単体テストで確認し、実際のOS上のsync/rename失敗注入とは区別する。

最終の実行結果と独立レビュー結果は作業報告に記載する。実KB、精密な速度・RAM計測、Linux実行は対象外。既存索引・他worktree・保存済み記録を変更せず、commit・push・公開・削除は行わない。

## ローカルの追加確認

実際のv3ファイルは1,000文書でliteral 1,435,453 bytes、normalized 1,433,396 bytes。v2比49.46%・49.26%減。モデルとの差はsource rootの長さ情報8 bytesと文字列134 bytes。100文書ではliteral 147,420 bytes、normalized 147,074 bytes。rootの文字列自体はレポートへ出していない。

100・1,000文書×両mode×14語の56条件で、v2検索・v3検索・scanの全出力が一致し、Pythonによる独立した期待文書集合にも一致した。両modeで差分更新を再実行しても保存バイトは一致した。

独立Zigレビューでは、保存前にも復元後の配列容量制限を適用する必要があるとのP1指摘を受けた。encoder/decoderの`ArrayBudget`共有と確保前の境界テストで修正し、対象箇所の再確認で追加指摘なし。v2読取の配列予算は2GiBに設定する。v2では文書配列32 bytesに対して符号化は最低17 bytes、postingとID配列40 bytesに対して最低26 bytesで、各配列の合計は符号化の2倍未満。従来の1GiB未満のCLI索引を新しいv3用予算だけで拒否しない。大きなv2からv3を作る場合は新規保存前の1GiB予算で停止し、旧索引を残す。巨大な実索引では未検証。

並行writerのロックは追加していない。同じ索引への同時実行を避ける前提であり、ファイル集合を読む間の外部編集についてもトランザクション保証はない。独立レビューはcodec・所有権・上限計算のコード追跡で、巨大入力や並行writerの実行検証ではない。

最終コードで`mise run check`、既存CLI11件、差分更新CLI6件、容量集計4件、`git diff --check`が成功。容量レポートにroot文字列がないこと、保存したソースSHA-256と最終コードが一致することを確認した。

## 変更なし差分更新の局所試作

全ファイルの読取・旧索引の完全復号検証・root/mode照合を維持する。差分判定で、文書数・パス・本文のバイト列・文書順がすべて一致した場合だけ、`Result.index = null`を返して新postings構築とencode・保存を省く。同じ集合でも文書順が違えばIDを付け直す通常経路を使う。重複パスの検査も維持する。

呼び出し側はnullを未変更の検証済みsnapshotとして扱い、旧索引の件数から従来と同じ完了表示を生成する。表示成功後だけprofileの成功状態を設定して終了する。表示確保や書込に失敗しても索引には書き込まない。索引bytes・mtime・inodeは維持する。未変更の場合に保存先の書込権限を要求しなくなる点は意図した変更。

mtimeのみ判定、checksum・varint・件数検査の省略、v2の暗黙変換は行わない。既存の追加・変更・削除経路の契約は維持する。原文集合の読取中に外部編集がないこと、同じ索引への並行writerを起動しないことも従来の前提のまま。

試作前の全差分・未追跡ソース・実行ファイルをworktree内`.local/storage-evaluation/noop-trial-01/before/`へ保存した。既存v3記録・他worktreeは変更していない。試作の正しさ確認後、別の測定担当によるA/B合成スモークを完了した。変更なし時はbytes・mtime・inodeを保持し、10件本文変更では通常経路を使うことを確認。条件・数値・識別情報はローカルの最終整理記録に保持し、背景負荷下の少数試行から一般的な速度効果を断定しない。

## 統合前の確認状態

v3・差分更新・早期終了は同じ専用worktreeにあり、ランキングや検索試作との実統合は行っていない。最終の製品ソースは追加測定時のSHA-256と一致する。正しさの最終実行は`mise run check`、差分更新CLI10件、既存CLI11件、容量集計4件で成功。早期終了の独立レビューも追加指摘なし。

未検証は実KB、Linux実行、巨大索引、冷キャッシュ、負荷統制下の性能、並行writer、読取中の外部編集、OS上のsync/rename失敗注入。同期・置換の失敗は共通保存関数の注入テストで確認し、実OSの障害検証とは区別する。

## literal少数更新の追加調査（2026-11-15）

`fd64096` を基準に、実KBから独立した合成2群で0・1・10件変更を比較した。各群1,200文書・9,741,600 UTF-8バイトで、共有本文群は2,775 unique gram / 3,201,558 posting ID、多様本文群は66,167 gram / 3,194,680 ID。固定seedで生成し、変更対象・追記内容を固定した。実KBの内容や検索語は取り込んでいない。

通常のReleaseFast版で予熱2回後に各条件20組、全再構築/差分更新と基準版/候補版の順序を交替した。同じroot・出力パスを使い、毎回初期索引を復元した。復元と正しさ確認は計測外で、各実行後の保存bytesは全再構築と一致し、0件変更の差分更新ではmtime・inodeも維持した。計装版は各5組で原因調査だけに使用した。

この作業のビルド・テスト・別ベンチは測定と重ねていないが、ホスト全体の負荷は統制していない。[性能測定の協調](development.md#性能測定の協調)に従い、以下はウォームmacOSのスモーク観測であり、性能改善の採用根拠や保証にはしない。

| 群・変更数 | 基準版 全再構築 | 基準版 差分更新 | 候補版 差分更新 |
| --- | ---: | ---: | ---: |
| 共有・0件 | 99.57 ms | 58.02 ms | 57.88 ms |
| 共有・1件 | 101.46 ms | 132.57 ms | 113.60 ms |
| 共有・10件 | 95.63 ms | 125.81 ms | 107.82 ms |
| 多様・0件 | 183.41 ms | 63.16 ms | 63.02 ms |
| 多様・1件 | 181.03 ms | 157.20 ms | 134.91 ms |
| 多様・10件 | 181.17 ms | 165.74 ms | 142.90 ms |

数値はCLI起動から終了までの中央値。共有群で速度逆転を再現したが、多様群では再現しなかった。1件変更が10件変更より大幅に遅くなる現象も安定して再現しておらず、実KBでの差をこの結果だけで説明できない。

候補は旧postingのgram検索を文書IDごとからpostingごとの初回にまとめる変更だけ。再利用区間は共有群で約30–31→12 ms、多様群で約40→17 msとなり、反復hash処理の削減と整合した。旧索引のchecksum・復号は約33–35 ms残り、共有群では候補も全再構築より遅い。その他に本文読取、差分構築、ID整列・配列移譲と一時map/deltaの解放、符号化、保存・同期、旧索引解放、残差を記録した。区間中央値の和は総時間中央値とは一致しない。

通常版のCPU・RSS・IQR・min/maxと個別サンプルも保存した。候補の差分更新中央値は短い一方、共有1件のp95参考値（各20標本）は152.77→162.40 msと大きく、tail改善は確認できない。候補でZigテスト・差分更新CLI13件が成功し、所有権・参照寿命・失敗経路の独立レビューで指摘はなかった。

**採用保留**。候補patch・計装ソース・バイナリ・個別結果・hashを `.local/integration/pr14-followup/` と `.local/benchmarks/followup-*` に保全し、製品ソースの変更は戻した。採用には負荷を統制した比較が必要。Linux、実KB、冷キャッシュ、異なる変更分布での効果は未確認。
