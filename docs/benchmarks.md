# 検索ベンチマーク

## 評価するもの

同じ合成文書群・検索語・実行ファイルで、索引を使う検索と全文走査を比較する。評価軸を次のように分ける。

- 正しさ: 索引検索と全文走査の出力が一致し、Pythonの文字列部分一致で求めた文書・行番号とも一致するか。
- 検索語の妥当性: 手作りの利用場面に対して、選んだ連続文字列で期待した文書に到達するか。
- 速度: 索引構築と、索引検索・全文走査のCLI実行時間。
- 容量: 保存済み索引のバイト数と、各CLIプロセスの最大常駐メモリ量。

検索結果はパス順で、ランキングは未実装。検索語の妥当性の確認は順位の良さや実際の利用者満足度の評価ではない。性能比較のために検索条件を変えず、1文字、一般的な語、希少な語、該当なしなどの条件を分けて見る。

## コーパスと正解の基準

`scripts/benchmark_corpus.py` がseed `20261114` で100・1,000・10,000文書を生成する。各サイズには日本語・英語・混在の手作り文書が2件ずつあり、残りはUTF-8で約1 KiBの合成Markdownとする。3種類の言語構成はほぼ均等。文書ごとに独立した固定乱数列を使うため、小さいコーパスの文書は大きいコーパスにも同じ内容で含まれる。

検索語は14種類で固定する。日本語・英語の1コードポイントと2コードポイント、長い語句、頻出語、希少語、該当なし、日本語・英語それぞれの「必要な2-gramはあるが連続一致しない」語句を含む。実際の検索履歴から抽出したものではなく、機能の分岐と利用意図を確認するために用意した条件である。合成文書は限られた定型文の繰り返しを含むため、実文書の語彙やgram分布を代表しない。

各検索語で索引検索と全文走査の標準出力全体を比較する。別途、Pythonの `str.find` と改行数から期待する文書・最初の行番号を求め、両方のコマンドの結果を照合する。利用意図の確認では、手作り6文書に限定した事前の期待集合と結果を照合する。抜粋の正確さをPython側で独立に再実装して照合するものではない。

manifestには文書ごとの相対パス・サイズ・SHA-256と検索語を保存する。コーパス全体のSHA-256は、相対パス順に `相対パスUTF-8 + NUL + 本文バイト列 + NUL` を連結して求めるため、生成先の絶対パスに依存しない。

## 測定方法

同じReleaseFastビルドを使用し、コーパス生成・正しさ検証と時間測定を分離する。各CLI実行を新しいプロセスとして起動し、親プロセスの単調増加時計で終了までを測る。

索引構築は5回、各検索語の各方式は予熱2回の後に30回測定する。検索語の順序は固定seedでラウンドごとに入れ替え、`search` / `scan` の先後も交互にする。すべて逐次実行し、同一条件の中央値とp95を記録する。p95は昇順に並べた `ceil(0.95 × 件数)` 番目を使うため、索引構築5件のp95は最大値になる。少数標本のp95や数msの差を安定した性能保証としては扱わない。

| コマンド | 実行時間に含まれる処理 |
| --- | --- |
| `index` | ディレクトリ走査、全対象文書の読み込み、N-gram構築、索引の符号化、書き込み・同期・置き換え、完了表示 |
| `search` | 索引の読み込み、チェックサムと保存形式の検査、復元、索引検索、抜粋作成、全結果の出力 |
| `scan` | ディレクトリ走査、全対象文書の読み込み、全文走査、抜粋作成、全結果の出力 |

したがって、検索の数値はメモリ上の検索アルゴリズムだけの時間ではない。索引検索は文書のスナップショットも読み込むため、保存形式のサイズや復元処理も含めて比較する。CLI出力は破棄しても、その生成と書き込みは測定に含まれる。

ファイルキャッシュを破棄せず繰り返すため、主にウォームキャッシュの条件を扱う。コールド起動、ディスク固有の性能、別OS・CPUへの一般化は評価しない。RSSは各子プロセスの最大常駐メモリ量であり、allocatorの使用量やシステム全体のメモリ消費ではない。

索引には文書の絶対パスが含まれるため、保存サイズは生成先のパス長にも依存する。同一コーパスでも別のディレクトリで生成した索引のサイズが完全に一致するとは限らない。

## 2026-11-14の初回測定

run-idは `baseline-01`。00:33:11〜00:34:52 JSTに測定した。測定時のリポジトリHEADは `be6f852a84f2c92d3bd23bd92a28b8ca9dee6786` で、対象のZigソースに未コミット変更はなかった。Zig 0.17.1のReleaseFast、Python 3.14.7、macOS 26.6.2 / arm64の環境を使用した。同端末で別途読み取った実験条件はApple M4、メモリ16 GiB、論理CPU数10。計測プロセス内ではCPU型番・メモリ容量の取得が権限制限で失敗していたため、要約JSONでは元の測定metadataと `supplemental_hardware` を分けて記録する。計測スクリプトは未コミットの状態だったため、そのSHA-256を保存して識別する。

全42条件（3サイズ × 14検索語）で、索引検索と全文走査の出力一致、Pythonの正解との文書・行番号一致、手作り文書の期待集合との一致を確認した。5回の索引構築、各条件・各方式30回の測定が完了し、計測前後の実行ファイルのハッシュも一致した。

全検索語の中央値・p95・RSS・一致件数、各コーパスのSHA-256、実装とスクリプトのSHA-256、環境情報は[保存した要約JSON](benchmark-results/baseline-01.json)に記録した。測定バイナリのSHA-256は `2ca0cf4947f2262b603742362d139ae90259276f2b9e6fda075608ab5f9be257`。以下のMiBは1,048,576バイトとする。

この環境・合成コーパスでは、すべての条件で保存済み索引を使うCLIの中央値が全文走査CLIより短かった。ただし、1文字の検索でも索引CLIが速い。1文字は内部で全文走査へ切り替わるため、この差を転置インデックスの候補絞り込みだけの効果とは説明できない。1ファイルからの復元と多数のMarkdownの走査・読み込みを含む、CLI全体の違いとして扱う。

索引は本文の約2.64〜2.77倍のサイズで、10,000文書の検索RSSは全文走査より大きかった。該当なしでも約40 msかかることから、検索語の一致件数以外にも固定的な処理コストがあると考えられる。読み込み・チェックサム・復元・メモリ確保のどれが支配的かは、この測定だけでは確定しない。

## 冗長な複製の削減と再測定

初回測定後、検索コマンドが索引の入力バイト列をarenaに保持したまま、復元時に本文・gramの参照先を複製していることをコードで確認した。読み込み済みのバッファを `storage.decodeOwned` に所有権ごと渡し、複製を省く形に変更した。復元後は `StoredIndex.deinit` で解放し、失敗時も入力を解放する。借用入力を複製する既存の `decode` の契約、保存形式1、検索条件は維持した。

2026-11-14 00:40:23〜00:42:02 JSTに `revised--01` として再測定した。測定時のHEADは初回と同じだが、`src/main.zig` と `src/storage.zig` に未コミットの変更を含む。測定済みの実装はコミットIDだけでは特定せず、[再測定の要約JSON](benchmark-results/revised--01.json)に記録したソースとバイナリのSHA-256で識別する。再測定バイナリのSHA-256は `00a034fcd28e7e659fd9c6072c4570c480943dbb88e8c976bae55af6ebd24673`。

コーパスのハッシュ、本文サイズ、言語構成、14検索語、計測スクリプトのハッシュ、保存形式と索引サイズは初回と一致した。両run-idの長さも揃えた。全42条件で正しさと手作り文書の期待集合を再確認し、5回の構築・各方式30回の測定を完了した。

| 文書数 | search中央値 ms 初回 → 再測定 | search RSS中央値 MiB 初回 → 再測定 | 同一検索語のRSS削減率 |
| ---: | ---: | ---: | ---: |
| 100 | 2.26〜2.34 → 2.30〜2.47 | 2.28〜2.33 → 2.06〜2.11 | 8.2〜9.6% |
| 1,000 | 6.09〜7.16 → 5.97〜7.00 | 8.48〜8.72 → 6.14〜6.38 | 26.6〜27.8% |
| 10,000 | 40.27〜50.09 → 38.36〜48.18 | 70.91〜72.73 → 46.95〜48.94 | 32.7〜33.8% |

10,000文書では、各検索語のRSS中央値が約23.8〜24.0 MiB減ったため、メモリ削減を根拠に採用した。CLI時間の中央値は同じ検索語で約3.4〜5.4%短くなったが、p95の変化は約8.1%減〜11.5%増と混在した。小さいコーパスでは時間が増える条件もあり、速度改善の保証とは扱わない。

対照となる10,000文書の `scan` 中央値は130.40〜137.31 msから130.47〜136.27 ms、索引構築の中央値は256.15 msから250.08 msとなった。変更していない経路にも変動があるため、時間の小差は実行環境の揺らぎを含む。保存サイズは同じで、コピー削減後も索引検索のRSSは全文走査より大きい。

### 未検証事項と次の候補

速度をさらに分解する必要が生じたら、ファイル読み込み・復元・メモリ上の検索・出力を個別に計測する。現時点で速度目標は設定しておらず、この結果だけを理由に圧縮・並列化・検索方式の変更へ進めない。ランキングや同義語、実文書の検索履歴に基づく評価は未実施である。

## 再現手順

リポジトリのルートで実行する。Python 3とmiseで固定したZigが必要。runnerは指定された実行ファイルを使うため、ReleaseFastのビルドを先に行う。

```sh
mise exec -- zig build -Doptimize=ReleaseFast \
  --prefix .local/benchmarks/release \
  --cache-dir .local/zig-cache-benchmark \
  --global-cache-dir .local/zig-global-cache
python3 scripts/benchmark.py --run-id reproduction-01 \
  --sizes 100 1000 10000 --index-repeats 5 --repeats 30 --warmups 2 \
  --seed 20261114

# 公開する場合は、個人パスや未知metadataを除く要約へ変換する
python3 scripts/benchmark_report.py \
  .local/benchmarks/reproduction-01/results.json \
  docs/benchmark-results/reproduction-01.json
```

生成先が既に存在する場合は上書きせず失敗するため、再実行時は未使用のrun-idを指定する。結果は `.local/benchmarks/<run-id>/results.json` に保存される。測定中は実行ファイル・文書・スクリプトを変更せず、他の負荷も避ける。runnerは実行ファイルのハッシュ不変とサンプル件数を検査するが、マシン負荷の統制は行わない。

## CIでの結果確認

[CIの定義](../.github/workflows/ci.yml)はUbuntuで検査・テストとベンチマークを独立したジョブとして実行する。`benchmark` は `check` の完了を待たず、専用のReleaseFastビルドで100・1,000文書を測定する。ジョブ内の各CLI測定は引き続き逐次実行する。索引構築3回、各検索方式5回、予熱1回の軽い条件で正解との一致と計測完了を確認し、Job summaryと公開用JSONのartifactを出力する。JSONへの変換はローカルと同じ `scripts/benchmark_report.py` を使い、raw・生成文書・索引・バイナリはartifactへ含めない。

この文書のmacOSでの初回・再測定とはOS、ホスト、サンプル数が異なるため、CIの時間を直接比較しない。別のCI実行でもrunnerの変動を含む。CIは性能の閾値や過去結果との自動比較で合否を判定しない。正しさの失敗やコマンドの失敗は通常のテスト失敗として扱い、速度・RSSは条件付きの観測値として実行画面から確認する。

## 記録の扱い

生成文書と生の測定値はGit管理対象外の `.local/` に配置する。実文書は読み込まない。公開用の `docs/benchmark-results/` には、allowlistで選んだ再現条件と集計結果だけをGitで管理する。OS・CPU・メモリ・ツール版は実験条件として残し、ユーザー名を含む絶対パス・ホスト名・生の失敗診断・未知metadataは公開しない。生成物への参照は `$RUN` 基準とし、rawはローカルにそのまま保持する。

`scripts/benchmark_report.py` はrawを変更せず要約を生成する。別途取得したハードウェア条件は `--hardware-metadata <JSON>` で指定でき、`cpu_model` / `memory_bytes` / `logical_cpu_count` だけを由来付きの補足として残す。要約JSONには生のサンプルを含めないため、ローカルのraw結果を削除した後は、別のパーセンタイルや外れ値除外で再集計できない。固定seedと記録したスクリプトからコーパスは再生成できるが、過去と同じ実行時間は再現できない。
