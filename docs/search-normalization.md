# 検索の正規化

## 検索条件

既定の `literal` は原文の完全な連続部分一致。`normalized` は本文と検索語を次の同じ手順で変換してから連続部分一致を調べる。

```text
NFKC → localeに依存しないdefault full case folding → NFKC
```

検索の中核（2-gram、候補集合、連続一致、保存）はZigで実装する。Unicodeデータ、コードポイントの分解とfolding、合成対の判定は固定版utf8procを使う。canonical ordering、合成を妨げる結合文字の判定、原文への由来追跡はZig側で実装する。使用版・取得元・チェックサムは [vendor/utf8proc/SOURCE.md](../vendor/utf8proc/SOURCE.md) に記録する。システムにインストールされたUnicodeライブラリは参照しない。

| 例 | normalizedでの扱い |
| --- | --- |
| `ＡＢＣ１２` / `abc12` | 同じ |
| `ｶﾞﾗｽ` / `ガラス` | 同じ |
| `か` + U+3099 / `が` | 同じ |
| `㌔` / `キロ`、`①` / `1` | 同じ |
| `Straße` / `STRASSE` | 同じ |
| `σ` / `ς` | 同じ |
| `か` + 独立した濁点U+309B / `が` | 異なる |
| ひらがな / カタカナ、長音、送り仮名、同義語 | 同一視しない |

空白は文字列の一部であり、単語分割、空白圧縮、trim、AND検索をしない。ただしNFKCによって全角空白やNBSPが通常の空白になることはある。アクセントや濁点を除去しない。ZWJ・異体字セレクタ等のdefault-ignorable文字も保持する。不可視文字の除去を含む標準の `NFKC_Casefold` とは別の検索プロファイルである。

## CLI

```sh
zigurui index --mode normalized /path/to/notes .local/normalized.idx
zigurui search --mode normalized .local/normalized.idx 'ガラス'
zigurui scan --mode normalized /path/to/notes 'ガラス'
zigurui search --mode literal .local/normalized.idx 'ｶﾞﾗｽ'
```

`--mode` はサブコマンドの直後に置く。省略時はすべて `literal`。索引から既定モードを推測しない。

| 索引のmode | 検索mode | 経路 |
| --- | --- | --- |
| literal | literal | 原文2-gramで候補抽出し原文照合 |
| normalized | normalized | 正規化2-gramで候補抽出し正規化本文照合 |
| normalized | literal | 保存原文の全文走査 |
| literal | normalized | `IndexModeMismatch`。normalized索引の再構築が必要 |

正規化後が1コードポイントの検索語は全文走査する。例えば `ｶﾞ` は合成後1コードポイント、`㌔` は展開後2コードポイントとなる。空検索語と不正UTF-8は拒否する。

## 原文位置と抜粋

検索結果は正規化本文で最初に一致する区間を選び、含まれるすべてのコードポイントの由来を覆う原文のUTF-8バイト区間 `[offset, end)` を返す。結合文字の並べ替えにより由来は非単調なので、区間の最初と最後だけで位置を計算しない。原文の最小開始位置となる一致を選ぶ、という契約ではない。

例として `前㌔後` を `ロ` で検索すると、原文では `㌔` 全体の `[3, 6)` が返る。`a U+0315 U+0300` の正規化は `à U+0315` となり、`à` の由来の包含区間には途中のU+0315も含まれる。原文をその範囲で切り出して正規化しても、検索語と完全一致するとは限らない。

行番号は原文の開始位置までの改行数から計算する。抜粋は原文のまま、一致開始の前32・開始から96コードポイント以内、改行までを表示する。UTF-8コードポイント境界を守るが、字素境界の保証や強調表示はしない。長い一致・改行を含む一致は抜粋に全体が収まらないことがある。

## メモリとサイズ制限

正規化本文と由来表は索引に保存しない。索引構築時は一文書ずつ変換してunique gramを複製し、検索時は候補文書を一つずつ変換・照合・解放する。scanも同じ変換を全対象に使う。原文は従来どおり保存されるため、検索は保存時点の本文を表示する。

非ASCIIを含む入力は、入力と各中間表現をそれぞれ4,194,304コードポイントまでに制限する。超過は `NormalizationTooLarge` でコマンド全体が失敗し、対象を黙って省略しない。ASCIIだけの入力は小文字化でバイト位置が変わらないため由来表を作らず、この追加制限の対象外となる。従来の文書64 MiB・索引1 GiBの上限は両モードに適用する。

由来追跡はコードポイント値・CCC・原文開始/終了位置を持つ要素を使い、変換中は入力・出力の二つの表現を保持する。配列の余剰容量や元本文、出力バッファも必要なので、コードポイント上限はRSSの固定上限ではない。処理用の解放可能なallocatorを原文読取用arenaと分離し、文書を跨いで派生データを溜めない。

## 索引の互換性

保存形式はv2。mode、変換手順の版、Unicodeデータ版をチェックサム対象として保持する。形式v1、未知mode、異なる変換版・Unicode版は明示的に拒否し、再構築を案内する。literalのプロファイルにはUnicode版を持たせない。旧索引の自動変換や自動上書きはしない。

正規化規則・Unicodeデータ・gram仕様や非互換な保存形式を変更した場合は再構築する。ライブラリの修正が変換結果を変える場合も変換手順の版を更新する。ライブラリ版の変更だけで自動的に互換と判断しない。抜粋のみの変更は通常、索引の再構築を必要としない。

## 検証と今後の範囲

単体テストは、採用版のUnicode `NormalizationTest.txt` 全5列のNFKC期待値、`CaseFolding.txt` のC/F、utf8proc全体変換との照合、手書きの原文バイト区間、allocation failureを扱う。索引とscanの一致だけで正解とせず、文書集合・位置の独立期待値も検査する。CLI結合テストは原文抜粋・保存スナップショット・literalへの切替・旧索引とmode不一致のエラーを確認する。

テストは公開Unicodeデータと合成文書のみを使用する。個人ノート、実検索語、個人パス・ホスト情報は含めない。実KBでの検索品質、normalizedの速度・RSS・索引サイズは未測定。かな種、長音、送り仮名、同義語、複数語、ランキング、正規化の既定化はこの実装に含めない。
